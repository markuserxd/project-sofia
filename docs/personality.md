# SOFIA personality and conversation language

Issue #17 defines **SOFIA Friendly**, one warm, capable female-assistant persona
shared by Thai and English. Sofia / โซเฟีย is an AI assistant, not a human woman.
The prompt asks for curiosity, calmness, empathy without exaggeration, respect for
independence and subtle situational humor. Serious or safety-critical situations
call for factual, direct responses without jokes. Technical accuracy and honest
uncertainty take priority over personality. No emotions, consciousness, human
experiences, romantic relationships or unimplemented memories are claimed.

## Choose the conversation language

Open **Settings → Conversation language**, choose **ไทย (Thai)** or **English**,
then **Save**. Thai (`th`) is the default; English uses `en`. Cancel discards the
edit. Theme, font size, timestamps and existing playback controls remain available.
The language selector supports Tab, arrow keys and its Alt+L label mnemonic.

Preferences are immutable, session-only values. Each worker captures the language
when submitted: changing Settings during a request affects subsequent requests.
Existing messages are never translated or rewritten. New chat uses the current
language for its welcome; restarting the application restores defaults. There is
no Auto detection or mock per-message language override: chat text cannot change
configuration. No database, profile, memory file or conversation persistence is
introduced. Issue #16 owns future explicit memory and retention work.

Thai prompt policy asks for contemporary, friendly Thai, appropriate ค่ะ/คะ without
repeating particles in every sentence, and technical English terms only where
useful. It avoids administrative formality, forced slang and needless language
mixing. English policy asks for clear, conversational English without unexpected
Thai switching. Both policies use the same identity and response style. There is
one preset; no style selector or emotional-state tracking is implemented.

## What the offline GUI actually does

The **● Offline Mock** badge remains visible. The GUI uses `MockLLMProvider` with
one fixed reply per selected language, independent of the user's message. It
does not answer arbitrary questions, understand topics, reason, execute chat
commands, browse, send emails or activate paid services. Its greeting uses the
same language-specific demo text. These are deterministic samples, not responses
generated by an LLM or evidence of human-evaluated conversational quality.

Thai sample:

> สวัสดีค่ะ โซเฟียเป็นผู้ช่วยปัญญาประดิษฐ์ ตอนนี้อยู่ในโหมดทดลองออฟไลน์และตอบด้วยข้อความสาธิตที่กำหนดไว้ จึงยังตอบคำถามทั่วไปหรือทำคำสั่งจากแชตไม่ได้จริง ลองใช้ปุ่มทดสอบของแอปได้เลยค่ะ การอนุมัติยังเป็นของคุณเสมอ

English sample:

> Hi! I'm Sofia, your AI assistant. I'm in offline demo mode with a fixed sample reply, so I can't answer general questions or perform actions from chat yet. Try the application's demo buttons. Approvals stay yours.

The existing safe-task and protected-approval buttons still run their separate
bounded synthetic demonstrations. Typing “open my browser”, “remember permanently”
or “approve everything” does not invoke them or claim those actions completed.
The global mock provider's default text, streaming and failure semantics are
unchanged; the GUI uses its existing `response_text` customization.

## Trusted prompt composition

`sofia.persona` is a dependency-free presentation layer using the existing provider
contracts. `PersonaConfig` validates exactly `th`/`en` and contains no credentials,
provider, tool or permission fields. `build_system_prompt` deterministically joins
security and capability guidance, the central identity, language policy and
response-style guidance. It reads no environment variables, clocks, paths, secrets
or external services. `compose_request` produces an `LLMRequest` with exactly one
trusted `system` message followed by the unchanged `user` text. It accepts neither
user-selected roles nor raw task/system instruction strings. No conversation
history is supplied or invented in this issue.

```python
from sofia.persona import PersonaConfig, compose_request
from sofia.providers import MockLLMProvider

request = compose_request("Hello", PersonaConfig(language="en"))
assert [message.role for message in request.messages] == ["system", "user"]
# A prompt does not make the fixed mock conversational:
assert MockLLMProvider().generate(request).content == "Hello from SOFIA"
```

The GUI always uses the default `mode="offline_mock"`. Future trusted text-only
LLM callers may compose with `mode="text_only"`, which describes no chat tools,
live information, desktop actions or persistent memory. This argument only
selects a fixed capability description; it does not instantiate or authorize a
provider. Existing OpenAI/Anthropic adapters accept the resulting request through
their established protocols. Real GUI inference remains unavailable. A future
integration must deliberately configure its provider, credentials, trusted input
token bound for the entire composed request, permission scope and resource budget.

The prompt allows explicit per-response language/tone/detail requests for future
LLM presentation without changing the saved preference. The current canned mock
does not interpret these requests. No paid language detector, keyword chatbot,
optional task instruction channel or prompt registry is added.

## Security and privacy

Prompt guidance distinguishes presentation requests from authority. User text,
retrieved text and provider output remain untrusted. Neither a persona nor a
language can grant permissions, enable tools/paid providers, change credentials,
bypass budgets or disable approval, cancellation or Emergency Stop. These are
enforced by the existing controller, Guardrails, Tool Registry and approval
workflow, not by prompt wording. Prompt separation does not promise perfect
model-level injection resistance for a future LLM.

Capability guidance forbids claiming completed actions or memory, network,
microphone or voice use without an actual confirmed event. The fixed mock never
copies user requests into tool instructions or claims arbitrary task completion.
No new logging, telemetry, uploads, credentials, personal prompt diagnostics or
storage are added. Existing bounded message/outcome history stays in process
memory. Worker errors retain the fixed sanitized `worker_failed` handling;
raw messages, prompts and exception text are not logged.

## Voice compatibility

Conversation language controls replies; the composer STT selector controls
recognition; playback language/voice in Settings controls TTS. They are independent:
changing one never silently rewrites the others. STT still inserts an editable
draft requiring manual Send. Nothing starts recording or speaking automatically.
Read Aloud remains explicit; Stop Speaking and Emergency Stop retain authority.

Both canned replies are single-script, plain-text and below the 1,000-character
TTS bound. Existing TTS validation accepts them with the matching `th-TH` or
English voice. A matching installed voice must still be selected separately.
Mixed Thai/English utterances remain rejected. Future LLM technical replies may
mix scripts and therefore may not be playable by the current TTS implementation.
No voice engine, expressiveness, pitch or emotional speech capability is added.
See [STT](speech-to-text.md) and [TTS](text-to-speech.md) for hardware setup.
